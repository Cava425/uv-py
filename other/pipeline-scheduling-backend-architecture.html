01设计结论与范围

产线调度是围绕现有 PipelineRuntime 建立的控制平面：负责形成触发事实、排队/准入、固定修订和参数快照、启动 Run，并将数据集输出和跨产线依赖收口为可审计的业务结果。真正的 DAG 执行仍由 PipelineRuntimeOrchestrator 及现有节点事件、轮询与物化链路负责。

核心原则：NDSP 只负责周期唤醒；MySQL 保存调度事实、游标、Attempt、租约和幂等约束。调度 Attempt 与 PipelineRun 分离；“DAG 完成”与“数据产出成功”分离；参数解析在持锁事务外完成，Run 创建及关键快照在事务内原子落库。

纳入范围

调度 CRUD 与不可变 Revision、配置校验、Cron/Misfire、手动运行/历史重放、共享串行队列、Cron 并行策略、上游依赖与 Fan-in、输出结果、租约恢复、Outbox、通知、灰度及健康巡检。

明确排除

前端交互；Pipeline DAG 节点本身的状态轮询和算子调度；Canvas/FMS/Spark 的内部执行细节；与调度无关的 NDSP 任务。现有节点轮询等仅作为调度运行依赖说明。

本文以代码现状为描述主线，并将规格要求与实现差异另行列出。规格目录 README 的“待实施”状态与当前代码事实不一致，不作为实现状态依据。

04调度定义、修订与生命周期

主档与不可变 Revision

PipelineSchedule 是长期稳定的调度身份，包含租户、业务 ID、名称、启停、当前修订指针、Cron 游标、rowVersion 和审计字段。PipelineScheduleRevision 固定绑定一组 pipelineId + pipelineVersionId，保存触发类型、时区、Cron/并发/Misfire 设置、依赖、参数模板、标准化 JSON 快照及 Hash，并具有 effectiveFrom/effectiveTo。

配置变更新增 Revision 并切换主档指针，不回写旧配置。Attempt 创建时记录其 Revision 和配置 Hash；已经排队的 Attempt 因此不会被后续编辑改写。名称单独变更不需要新修订；启停也只更新主档。重复编辑由 rowVersion 乐观锁防护。

创建/编辑时的校验要点

  • 租户有效产线及具体版本存在；同租户同产线版本只允许一个未删除调度绑定。保存时再锁目标 Pipeline 并检查，避免并发配置竞争。
  • 触发类型字段组合合法：MANUAL 不做自动触发；CRON 配 Cron、并发策略及 Misfire；UPSTREAM 配上游依赖、Correlation 表达式及版本策略。
  • 依赖别名和上游产线不重复；禁止自依赖、错误版本引用和有向环。并发编辑环检测按稳定顺序锁相关调度主档。
  • 参数节点/路径根据指定版本及算子 Schema 绑定；类型、标签、敏感标记等由服务端固化，不信任客户端传来的显示属性。
  • 修改生效边界关闭旧 Revision 的 effectiveTo，延迟到达的上游事件仍按其业务时间路由至正确历史修订。

启停与删除

  • 启用 CRON 时，以数据库当前时间初始化 lastEvaluatedFireAt，并计算严格晚于当前时间的下一个触发点；停用期间不积累 Misfire。
  • 停用阻止新的自动触发和立即运行，但不自动取消既有 WAITING 项；需要显式取消队列。当前代码停用时关闭 OPEN Fan-in。
  • 删除为逻辑删除。存在 WAITING、PREPARING、RUNNING 或 MATERIALIZING Attempt 时拒绝删除；历史 Attempt、Revision 等记录保留。
状态口径提醒：调度“停用”不是“清空队列”，现有等待实例仍可由 Dispatcher 执行。批量取消接口是独立操作，需在运维/调用流程中考虑。

05参数绑定、模板解析与 Manifest

静态参数覆盖模型

调度不修改版本节点定义。执行前读取所选不可变 Pipeline 版本的节点静态 JSON 参数，以 nodeId + parameterPath（RFC 6901 JSON Pointer）定位字段；将解析后的值按声明类型转换并覆盖，未配置的节点/字段继续使用版本静态默认值。数组只支持根路径整体覆盖，不支持数组元素路径覆盖。

模板类别格式/语义示例
时间变量基础量 triggerTime / now；支持按书写顺序做天/小时偏移，参数化 date/hour 格式。{{triggerTime - 1d + 2h}}
{{date(triggerTime - 1d)}}
{{hour(now)}}
上游变量已配置别名下的 datasetId、version、runId。{{upstreams.source.datasetId}}
类型转换String 保留文本；number/integer/boolean/array/object 转为真实 JSON 类型，并按完整节点 Schema 校验。valueType=object 时产出对象而非 JSON 字符串。

保存阶段由 ScheduleParameterBindingService 基于版本 Context 绑定节点与 Schema、规范化路径、校验重复绑定和模板格式。可由时间上下文静态验证的模板会模拟解析并验证完整节点配置；依赖上游值的模板延迟到运行时解析。预览为模拟，不等于未来上游一定能解析。

上游版本绑定策略

策略含义适用
PINNED引用配置时固定的数据集版本。输入必须可重复定位到指定版本。
CURRENT_VERSION使用数据集当前版本。手动触发等非事件绑定场景。
LATEST_RUN依业务时间选取对应上游产线版本下最近成功物化输出。按业务批次取最近已产出结果。
TRIGGERED_RUN使用本次上游 Fan-in 当前成员所关联的 Run/数据集版本。严格沿上游事件传递该批次数据；重评估/立即运行需要显式绑定上下文。

required 上游解析失败会阻止下游运行；optional 上游解析失败不以空值覆盖目标参数，继续沿用静态默认值。运行前解析器会确认 required 版本并写入解析事实。

运行 Manifest

真正创建 Run 时，Attempt 固化：templateSource、resolvedOverrides、finalNodeParams、upstreamResolution 和 manifestHash。Runtime 用有效参数构造 NodeRun；未覆盖节点从版本静态参数读取。该快照支撑审计和精确重放。

解析与事务分离：较重的节点查询、模板渲染、上游版本解析及类型校验在写事务/行锁外完成。随后在 Launcher 事务中重新确认 Revision 指针（立即运行/普通派发）或按历史 Revision 特例放行（Replay），再行锁准入和原子创建。

06三类触发流程

sequenceDiagram autonumber participant N as NDSP / API participant S as Schedule Service participant M as MySQL participant P as Parameter Resolver participant L as Launcher participant R as Pipeline Runtime participant O as Output / Outbox N->>S: Cron scan / 立即运行 / Fan-in 派发 S->>M: 读取 Schedule + 固定 Revision S->>P: 锁外解析参数与上游输入 P-->>S: 有效节点参数 + Manifest S->>L: 创建/派发 Attempt L->>M: 开事务、锁 Pipeline、检查资源/修订 L->>R: startRun(command) R->>M: 写 PipelineRun + NodeRun L->>M: 写 Manifest、RunOutput 初始行、Attempt-run 关联 M-->>L: COMMIT R-->>N: 提交后开始 DAG 执行 R->>O: DAG 完成后物化并终态收口

MANUAL / 立即运行

Controller 调用 Service，同步锁外解析当前 Revision；之后 Launcher 在事务内锁 Pipeline 并检查活动运行，创建 Attempt、Run、NodeRun、RunOutput 和关联。忙碌返回冲突，不排队；立即运行类型记为 MANUAL_OVERRIDE。不改 Cron 游标。

CRON

扫描器按数据库时间取到期主档，逐个进入事务处理游标和触发实例；QUEUE 建 WAITING，SKIP 建带租约 PREPARING 并提交后直发。Dispatcher 对排队项认领并启动。

UPSTREAM

仅在上游 RunOutput 形成终态事实后由 Outbox 事件驱动。Fan-in 满足条件并封口后创建下游 WAITING Attempt；后续 Dispatcher 负责启动。Fan-in 失败时创建跳过 Attempt。

REPLAY

创建全新 Attempt，不改来源记录。EXACT_SNAPSHOT 复用来源有效节点参数和 Manifest；REEVALUATE 按来源 Revision 重新解析。重放在 Launcher 中不要求来源 Revision 是当前指针。

07Cron、Misfire 与并发控制

Cron 游标原子推进

  1. cron-scan 读取 DB_NOW 和有限批次到期调度（next_fire_at <= DB_NOW）。租户未放量时不推进游标，避免放量后静默丢失触发点。
  2. 加载主档当前 Revision 并解析五字段 Crontab。支持通配、数字、列表、区间、步长组合；不支持秒、年、Quartz 扩展字符或宏。
  3. 以游标区间枚举计划时间，最多 500 个/调度/轮；不超过 60 秒延迟按正常触发。超过阈值为 Misfire。
  4. 在同一事务中 CAS 更新 lastEvaluatedFireAt/nextFireAt 并创建触发 Attempt；游标推进失败表示其他轮次已处理，放弃本次。
  5. scheduleId + triggerKey 唯一索引是防重复的最终保障；重复唤醒插入冲突按幂等成功处理。
配置/策略代码行为
并发 SKIP“跳过排队、允许同版本并行”，不是跳过本次。Cron 事务生成 PREPARING 和租约，提交后直发；不受等待队列容量限制。内部 Runtime 命令仅对此 Cron 路径豁免活动运行门禁，但仍持 Pipeline 行锁。
并发 QUEUE每个触发点建立 WAITING，按触发时间 FIFO；每调度最多 100 个 WAITING，满额创建 SKIPPED/QUEUE_FULL 并告警。
Misfire SKIP每个漏跑计划点留一条 SKIPPED/MISFIRE_SKIP 审计记录，不补跑。
Misfire FIRE_ONCE最近 24 小时漏跑合并为一个补跑 Attempt，使用最近漏跑点作业务 triggerTime；24 小时外记录 MISFIRE_OUT_OF_WINDOW。单轮枚举受 500 点上限约束。

统一并发维度与最终门禁

串行准入按 (tenant, pipelineId, pipelineVersionId)，所以同一版本跨不同 Schedule 共享队列，不同版本可并行。PipelineRun 的 PENDING/RUNNING/PAUSED 与 Attempt 的 PREPARING 均视为占用。Dispatcher 的忙闲预检只是减少无效认领；最终门禁由 PipelineRuntimeOrchestrator 持有 Pipeline 行锁完成，防止两个入口同时检查空闲后双启动。

Dispatcher 对候选按并发维度去重，仅保留队首；Cron-SKIP 不参与同维度去重。租约 token 是 fencing 条件：过期执行上下文无法写入 Manifest/Run 关联。QUEUE 启动时若最终门禁发现资源被抢占，释放租约退回 WAITING，而不是误报参数失败。

时区实现注意：Revision 默认保存 Asia/Shanghai，Cron 计算使用 LocalDateTime；触发键 Epoch 秒转换读取 JVM 默认 ZoneId.systemDefault()。代码调用未显式把 Revision 时区传入 Cron 解析器，因此部署 JVM 时区必须核实为与业务配置一致，否则时间展示/触发键可能出现偏差。

08Attempt 状态机与运行状态隔离

stateDiagram-v2 [*] --> WAITING: QUEUE / UPSTREAM [*] --> PREPARING: CRON-SKIP / 立即运行 WAITING --> PREPARING: Dispatcher 认领 WAITING --> SKIPPED: Misfire / 队列满 / 上游失败 WAITING --> CANCELLED: 用户 CAS 取消 PREPARING --> RUNNING: Attempt + PipelineRun 原子创建 PREPARING --> WAITING: 租约超时且尚无 Run PREPARING --> RUNNING: 租约超时但 Run 已存在 PREPARING --> FAILED: 参数解析/启动失败 RUNNING --> MATERIALIZING: DAG 成功且输出需物化 RUNNING --> COMPLETED: 输出终态成功 / 无需物化 RUNNING --> FAILED: DAG 失败 MATERIALIZING --> COMPLETED: MATERIALIZED / NO_VALID_DATA / NOT_APPLICABLE MATERIALIZING --> FAILED: 输出物化最终失败 COMPLETED --> [*] FAILED --> [*] SKIPPED --> [*] CANCELLED --> [*]

PREPARING 表示已认领/解析/建 Run 的内部阶段；MATERIALIZING 表示 DAG 已终态但输出业务结果尚未收口。API 内部状态准确返回，展示态会将 PREPARING 并入 WAITING、MATERIALIZING 并入 RUNNING。WAITING/PREPARING 等调度控制状态不加入 PipelineRun 枚举。

对已过期 PREPARING 租约：如果尚无 pipelineRunId，恢复为 WAITING 重新派发；如果 Run 已创建，校准为 RUNNING。Recovery 另行检查 RUNNING 对应 Run 已终态的滞后状态。恢复操作按条件更新保持幂等。

09PipelineRun 输出业务结果收口

启动事务先写唯一的 PipelineRunOutput 占位行（通知接收人及 Pipeline/版本快照）。DAG 执行和数据集物化完成后，输出服务把物化结果作为稳定业务事实保存，并推进关联 Attempt。

RunOutput outcome含义Attempt 结果
MATERIALIZED输出成功生成 DatasetVersion。COMPLETED
NO_VALID_DATA无有效输出数据。按业务成功收口，输出 outcome 保留为空数据事实。
NOT_APPLICABLE产线没有适用输出节点。按业务成功收口。
FAILEDDAG 执行失败或物化最终失败。FAILED，携带稳定原因码。

输出的过程状态为 NOT_REQUESTED / PENDING / MATERIALIZING / TERMINAL。DAG COMPLETED 不代表数据已成功物化；反之物化失败也不反向改写成功完成的 PipelineRun。直接运行没有 ScheduleAttempt，仍写 RunOutput 并能产生通知/上游事件。

输出结果状态推进、调度 Attempt 终态及 PIPELINE_OUTPUT_TERMINAL、SCHEDULE_ATTEMPT_TERMINAL Outbox 写入按同一领域事务组织。终态 CAS 未命中不重复发出不匹配的终态事件。

更新每个依赖的 current 成员"] PTR --> DECIDE{"required / optional 收敛判断"} DECIDE -->|required 全成功| READY["readyAt = now + 300s"] DECIDE -->|required 明确失败| FAIL["FAILED 封口"] READY --> SEAL["FanIn Seal Job 到期复核"] SEAL --> SAT["SATISFIED 封口 + 下游 WAITING Attempt"] FAIL --> SKIP["FAILED 封口 + SKIPPED Attempt"] FAIL --> FIX{"required 后续是否全部修复"} FIX -->|是且 Schedule 启用| REOPEN["roundNo + 1，重开并补建下游 Attempt"] FIX -->|否| KEEP["保持 FAILED，仅追加成员"]
  • 触发源是 PIPELINE_OUTPUT_TERMINAL，不是 DAG 完成事件，避免下游拿到尚未落地的数据集版本。
  • 按事件业务时间找生效中的下游 Revision，再通过依赖反向索引定位依赖别名、上游具体版本及 REQUIRED/OPTIONAL 属性。匹配不到、调度停用/删除或超出保留窗口（默认 7 天）会记录丢弃原因，不创建不可靠批次。
  • 聚合唯一维度为租户、Revision、Correlation Key；成员 append-only，以聚合行锁保护当前成员指针。一个依赖多个事件按 (businessTriggerTime,eventId) 选最新，同时保留历史事件。
  • required 全部物化成功后启动默认 300 秒收敛期；全 optional 依赖则在首个终态成员到达时启动同一收敛期。封口时再读取当前成员并复核，降低 Outbox 到达乱序影响。
  • required 失败/无数据会失败封口并创建 SKIPPED/REQUIRED_UPSTREAM_FAILED；Fan-in 失败状态可在全部 required 当前成员修复后增加轮次重开并自动补跑。已经 SATISFIED 的批次不会重复触发。
  • 下游参数策略使用聚合成员提供的上游解析事实。required 无法可靠解析时拒绝启动；optional 不覆盖目标参数，采用静态默认值。

Fan-in record-only 模式下仍执行聚合与封口但跳过创建下游 Attempt，用于核验 Correlation Key。版本变化后旧 Revision 已建立的 OPEN 聚合仍按原修订收口，不将新事件混入新旧快照。

11Outbox、通知、租约与幂等

事务 Outbox

业务事务内同时提交事实更新与 Outbox 事件，避免业务数据已提交、进程却在发消息前崩溃。Publisher 扫描有限候选，以 CAS 租约认领，调用唯一注册的 Handler 后标记发布；异常按指数退避，最多 8 次后 FAILED。未知事件类型作为死信；已知但暂时没有 Handler 的事件不认领，避免耗尽重试。

通知任务

终态 Handler 只在需要通知的结果创建 NotificationTask；通知调用在提交后由独立 Worker 投递飞书，不把外部网络请求放进业务事务。成功、运行失败以及 required 上游失败跳过会发通知；普通配置跳过及用户取消不打扰。接收人以 Pipeline Owner 快照为主、管理员群为兜底，卡片快照用于稳定重试。

通知失败重试固定为首次发送后 1、5、15 分钟，最多总计 4 次。飞书请求使用通知任务 ID 作为服务侧 UUID 去重键。通知 DEAD 只告警，不改变 PipelineRun 或 Attempt 的终态；dry-run 模式模拟成功收口，避免关闭演练后旧任务突然群发。

对象数据库幂等/竞争保护租约/重试
Cron Attempt(tenant,scheduleId,triggerKey) 唯一；游标 CAS。SKIP 直发和 Dispatcher 使用 lease token。
Outbox全局唯一 eventId；Handler 由领域唯一键去重。token + expiresAt；5 秒起指数退避，封顶 600 秒，最多 8 次。
Fan-in(tenant,revisionId,correlationKey) 唯一；成员以聚合+eventId 唯一。行锁保证 current 指针和封口/Attempt 同事务。
RunOutput(tenant,pipelineRunId) 唯一；终态不能覆盖。事务内与 Attempt 状态和 Outbox 同步推进。
Notification(tenant,idempotencyKey) 唯一。token + expiresAt；固定 1/5/15 分钟重试。

14租户边界与敏感信息

  • 用户 API 从认证上下文读取 lesseeCode 和操作人，不采信 Body 自带租户。后台 Job 全局扫描时，后续每条记录查询仍应按记录中的租户隔离。
  • 敏感字段由算子版本 Schema 和参数定义的 sensitive 标志识别。Context、校验/预览、修订详情、Attempt 详情和运行历史在响应构造时执行脱敏；无法识别 Schema 时历史详情倾向于整节点隐藏。运行查询只脱敏响应副本。
  • 敏感覆盖的 resolvedOverrides 记录以 ****** 替代具体值，并保留 sensitive/overriddenBySchedule 标记。该标记区分参数是否被调度覆盖，但不暴露明文。
  • 通知 payload 是脱敏卡片快照；日志/异常不应拼接完整请求参数。数据集 Owner 来源与 Run 执行主体分开，自动调度 Run 可由 SYSTEM_SCHEDULER 执行，但产出归属仍使用 Pipeline Owner。
重要安全事实：敏感值仍可能以明文存在于 Revision 的 config_snapshot，以及 Attempt 的 final_node_params（实际运行参数必须进入 NodeRun/运行上下文）。因此“接口响应已脱敏”不等于“数据库/备份无明文”。规格将此列为本期接受的数据风险；需按生产凭证数据等级配置 DB/备份/运维访问控制，并重新评估凭证参数是否应通过 Apollo 注入而非调度覆盖。

17架构亮点、难点与工作量

这不是简单的“定时器 + 调接口”，而是在既有 Pipeline Runtime 上补齐一套有审计、可恢复、可扩展的调度控制面。系统复杂度主要来自并发正确性、业务结果收口和跨任务可靠协作。

亮点 · 复用而不侵入

调度只负责编排和准入，通过 PipelineRuntimeOrchestrator 复用既有执行引擎；等待、跳过、取消留在 Attempt 域，不污染 PipelineRun 状态机。

亮点 · 数据库承载事实

NDSP 只周期唤醒，MySQL 中的游标、唯一键、事务、租约与 Outbox 构成可审计事实；重复唤醒和进程崩溃由持久化状态收敛，而非依赖内存锁。

亮点 · 版本与参数可追溯

调度绑定不可变 Pipeline 版本；Revision 固定配置，Attempt 固化 Manifest，支持复盘和历史重放；Schema 驱动参数绑定，未覆盖值继续沿用版本静态默认值。

亮点 · 输出事件形成闭环

以物化后的 RunOutput 作为跨产线依赖和通知事实源；Outbox + Fan-in 将异步事件、乱序到达、多上游收敛和下游派发串成可恢复链路。

主要难点

难点复杂性来源实现上的关键约束
并发与幂等多个 NDSP 唤醒、API 手动触发、跨 Schedule 共享产线版本资源；“先查空闲再启动”存在竞态。唯一键与游标 CAS 防重；最终准入落在 Pipeline 行锁及 Runtime；租约 token 防止过期执行上下文回写。
执行终态与业务终态DAG 成功不代表数据集已物化；物化失败也不应篡改已完成的 PipelineRun。独立 RunOutput 状态机收口，并在同一事务推进 Attempt 终态和 Outbox 事件。
参数与版本语义模板、JSON Pointer、数据类型、算子 Schema、上游版本解析和敏感字段共同影响实际执行。重参数解析放在长事务外；启动事务再次校验 Revision/租约并原子固化 Manifest；运行数据与 API 脱敏边界明确区分。
Fan-in 乱序与修复多上游终态到达顺序不确定，required/optional 规则、收敛窗口和失败后修复都影响是否派发。成员 append-only、按业务时间确定当前成员、延迟封口再复核；失败修复通过轮次控制，避免重复下游执行。
异步任务运维7 个 Job 各有独立积压、租约、重试、超时和灰度开关；频率还由 NDSP 注册侧配置。有界批次/时长、恢复任务、只读健康巡检和死信告警共同提供运维闭环。
